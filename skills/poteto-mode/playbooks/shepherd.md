### Shepherd

**You own one sweep, not the PRs. Each run clears what an agent can clear on every open PR the operator wrote, lands what is verified, and speaks only when something merged or needs the operator.** A scheduled task runs this playbook, locally or in the cloud. The task prompt is the operator's standing request. It names the GitHub owners to sweep, the merge grant (if any), each repo's approval bot and re-review command, and how to reach the operator.

Every run starts from GitHub's current state and keeps no state of its own, so a crashed or skipped run costs nothing and two runs in a row converge.

1. **List the queue fresh.** `gh search prs --author @me --state open --draft=false --owner <owner> --limit 200 --json repository,number,url,updatedAt` for each owner the task names. Drafts are the operator's work in progress, so leave them.
2. **Skip PRs someone is already on.** One writer per branch. Skip a PR whose head commit is under 30 minutes old, or whose number matches a running session's `prNumber` in `mcp__ccd_session_mgmt__list_sessions` (when the session has it). The listing names no repo, so a match in any repo counts, because a wrong skip costs one hour. A `gh stack` is one unit with one owner: skip the whole stack when any of its branches is busy, classify every open PR in it, and land only from the frontier, its lowest open PR.
3. **Classify each PR.** Run `scripts/merge-gate/merge-gate <pr> --repo <owner>/<repo>` without `--merge` (`--stack` on a stack's frontier). First drop two reasons that are not agent work: `threads-unresolved` when every unresolved thread's last comment is the operator's (it waits on the reviewer), and `base-not-trunk` on a stack PR above the frontier (it waits on the frontier). Then take the first rule that matches. This order replaces `playbooks/opening-a-pr.md` step 4's "any final reason is final" for triage only, because on a repo that requires a human approval every PR carries `needs-human-approval` and would never get an owner pass. Merging still obeys merge-gate.
   - `not-mergeable` with `DIRTY` or `BEHIND` on a PR in a `gh stack`, and no other "back to Babysit" reason: operator list, because restacking takes `gh stack rebase`.
   - Any "back to Babysit" reason from `playbooks/opening-a-pr.md` step 4: owner pass (step 4).
   - `changes-requested` from review bots only, with no bot review on the current head: owner pass, to run the re-review command.
   - `not-mergeable` with `mergeStateStatus=BLOCKED` while `gh pr view --json reviewDecision` reads `REVIEW_REQUIRED`, and the approval bot has no verdict on the current head: owner pass, because requesting the approval bot is agent work.
   - The approval bot's latest verdict on the current head is anything but an approval: operator list (step 6).
   - `not-mergeable` with `mergeStateStatus=BLOCKED` while `reviewDecision` reads `APPROVED`: operator list, since GitHub blocks it for a reason merge-gate does not name.
   - Any other transient reason: wait for the next run, unless the head commit is over 24 hours old, which puts it on the operator list with the reason.
   - A stack PR above the frontier, a frontier whose stack gets an owner pass this run, or no reason left after the drops: wait for the frontier or the reviewer.
   - Decision `merge`, or `needs-human-approval` as the only reason when the task's grant covers it: land (step 5).
   - Anything else: operator list.
4. **One owner pass per PR or stack with agent work.** Spawn a fresh background `pstack:poteto-agent` per PR, or per stack (bottom-up, each fix in the lowest PR that owns the code), with `isolation: "worktree"`, on the code delegates' model from `references/models.md`. Brief it to run one pass of `playbooks/babysit.md` in `drive` mode, then return. One pass means one push wave and replies citing the commit, read status with `scripts/watch-pr/watch-pr --owner <owner> --repo <repo> --pr <pr> --status-only` and never wait for CI. The owner is the branch's single writer for the pass, so on a PR off trunk it may resolve a `DIRTY` or `BEHIND` base itself, by rebasing onto trunk and pushing with `--force-with-lease` pinned to the head it read. A conflict in a `gh stack` is reported, not resolved. Once the PR has no unresolved thread, the owner runs the task's re-review command if a bot has not reviewed the head yet. Once the bots are clean and CI is green on the head, it requests the approval bot. It returns `done`, or `operator: <the one action needed>`, which joins the operator list. The run waits for every owner pass it spawned before step 6, so no pass outlives its run. The next run picks up whatever the pass left.
5. **Land under the grant.** Without a grant, put the PR on the operator list as merge-ready. With one, run `playbooks/shipping.md` steps 1 to 4 for it: an independent verifier, then `scripts/merge-gate/merge-gate <pr> --merge`, or the grant's own merge command when the grant covers the refusal. That one case overrides Shipping step 4's "leave the merge to the user" and Opening a PR's ban on `gh pr merge`, and only under a grant written in the task prompt. Read the PR back to confirm it merged.
6. **Notify on change only.** One message per run, sent through the session's push-notification tool, or else the channel the task names. It lists each PR this run merged, and the operator list with the one action each PR needs from the operator. Send the operator list only on the task's digest run (for example, the first run after 09:00 local), so an unchanged wait does not ping every hour. A run that merged nothing outside the digest run sends nothing.

**Reply:** one line per PR touched (action taken, or why skipped), the PRs merged, the operator list, and whether a notification went out.

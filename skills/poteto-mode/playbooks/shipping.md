### Shipping

**You own what lands. Verify each PR independently, land only the verified run from the root, then keep your hands off the stack.**

This is the half after `playbooks/babysit.md`. Run it only on an explicit request to land, merge, or ship.

1. **Verify each PR independently before it lands.** Every PR operation goes through `gh`. Never require Graphite (`gt`). One verifier per PR, each a background subagent with `isolation: "worktree"`, runs the change the way a user would with the matching control skill (such as the `claude-in-chrome` browser tools or the built-in `run` skill), parent against head, and posts `PASS`, `PASS+NOTES`, or `FAIL` on that PR. Only a verdict from an agent that did not write the code counts, because an author checks what it meant to build. Green CI and an approving bot review are not verdicts, because neither runs the change as a user would.
2. **Land only the contiguous verified run rooted at the bottom.** Walk up from the lowest unmerged PR and stop at the first one without `PASS` or `PASS+NOTES`. The PRs below it are the run, and the top one is the ceiling. A verified PR above an unverified one waits, because it cannot land without the code below it. Moving one out of a `gh stack` takes the interactive `gh stack modify`, so leave that to the user. Once its branch neither holds nor needs that code and it targets trunk, it can land on its own after a fresh verdict, because its old one ran with that code beneath it and trunk does not have it.
3. **Re-check that the verdicts still describe the code.** A verdict covers a patch, and a chain rebase moves every PR above it to a new SHA without failing any check. Compare `git patch-id` at the verdict SHA with the current head before trusting an older verdict. When the patches differ only in tests, docs, or lint config, a lane's result stands if what it ran builds the same at both SHAs apart from noise. Noise is a difference that also shows up between two builds of the verdict SHA, or an embedded commit SHA. Report each kind of noise with its files, so a reader can check the call. The change itself still gets fresh checks and a review, because the old verdict never saw it. A lane with no build output, such as a dev server, cannot show this, so rerun it, and re-verify anything else that drifted.
4. **Land bottom-up, one PR at a time.** Always merge the run's lowest unmerged PR. Bring its branch onto the exact trunk tip when needed, with `gh stack rebase --downstack` and `gh stack push` from the bottom branch, and re-run step 3 after the push. Merge with `scripts/merge-gate/merge-gate <pr> --merge`, which refuses a PR whose base is not trunk, because one whose base is still its parent's branch would merge into that branch. In a GitHub native stack, land the whole run at once with `scripts/merge-gate/merge-gate <ceiling> --stack --merge` instead. It gates every open PR from position 1 to the ceiling, each against the head of the PR below it, and lands them in one atomic merge-async call. A refusal stops the landing. For `needs-human-approval`, report the PR and the human-only files the gate listed, and leave the merge to the user. Read the PR back (`gh pr view <pr> --json state,mergedAt,baseRefName`), because a merge can report success when a merge queue only queued the PR. A landed PR reads merged with trunk as its base. Never arm `--auto`, because without required checks GitHub merges it at once. After a merge lands, GitHub restacks the rest of a `gh stack` server-side. Run `gh stack sync`, confirm the next PR now targets trunk, and let step 3's patch-id rule decide whether its verdict survives. Merge it once its checks pass and its verdict survives.
5. **Leave the stack alone while it lands.** Step 4's rebase, push, and sync are the only changes to a branch or base, because a merge lands whatever its branch and base hold at that moment, verdict or not. Use `scripts/watch-pr/watch-pr --queued-stack --stack-prs <bottom>` only as an event wake under `/loop` in dynamic mode, and after each wake read `gh pr view <pr> --json state,mergedAt,mergeStateStatus,statusCheckRollup` for the current PR until `mergedAt` is set. A base that moves to trunk when its parent merges is expected, not damage to repair. If a merge stalls, find out why before you change anything.
6. **Stop at the ceiling.** Extending the run takes new verdicts, so it is a new pass through step 1.

**Reply:** the verified run and its ceiling, each PR's verdict and who produced it, what landed and how you confirmed it, and what the next gap needs.

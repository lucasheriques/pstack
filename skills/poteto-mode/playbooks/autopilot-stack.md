### Autopilot-stack

**You own the stack, never the landing. Build and verify the queue with full autonomy, then hand the operator one linear base-branch stack to review and land.** The sibling of **Autopilot-full**.

1. **Run the owner loop unchanged.** Every PR operation goes through `gh`, and the stack goes through `gh stack`. Never use Graphite (`gt`). One background `pstack:poteto-agent` per PR, spawned with `isolation: "worktree"` (`"remote"` when it must outlive this session), owns its change end to end: build, first push, a draft PR opened before self-proof, self-proof (gates, CI, receipts), skeptical review-bot triage per `../references/bugbot-triage.md`, a slop-strip with the built-in `/simplify` skill, `/no-comments` (the **no-comments** skill), the pre-PR gate (**interrogate** against trunk, every finding fixed or dismissed), and babysit to green per `playbooks/babysit.md`. Owners parallelize when the work is self-contained. Within about 15 minutes, every owner starts a `decisions.tsv` trail per the **show-me-your-work** skill, pushes its first branch snapshot, and opens the PR as a draft. The owner marks it ready with `gh pr ready` only after self-proof passes and the interrogate gate is clean. Keep the trail uncommitted and return it in the report. Owners also keep the `children.tsv` of Autopilot-full step 2.
2. **Audit on the wake chain.** The root runs an audit tick roughly every 30 minutes, armed with `/loop 30m <tick prompt>`. Never leave the cadence to memory or lossy completion notifications. At each tick, re-read this playbook, then re-read the `/goal` objective. Audit the operation against both. Fix drift during that tick. Probe each owner with a generic liveness or status check. Count only side effects as progress: commits, pushes, PR or check deltas, and store reports. Treat a lane that passes its expected runtime without a side effect as stuck. Stand it down and dispatch a replacement at once. Do not wait for a polite return. Probe all subagents and end the tick per Autopilot-full step 6.
3. **Hold the operator gates.** State-then-wait, so a request to state the plan is not a go. On the operator's explicit go, hand the operator a `/goal <full program objective>` line to run, since `/goal` is a user command the agent cannot arm. The goal continues across turns until the chain is done. On the operator's stop, every owner takes an immediate zero-writes hold.
4. **Verify each round.** The owner reports its code-ready head SHA once the shipped code is final, and STACK-READY with the exact head SHA when its loop is green. The root verifies each round per Autopilot-full step 4, with STACK-READY in place of merge-ready. Nothing enters the stack unverified.
5. **Append on a clean verdict, never ship.** No owner merges, arms auto-merge, or closes. A clean verdict appends the PR to the one linear `gh stack`, in verified order or an order the operator specified.
6. **Single writer on topology, parallel writers on builds.** Owners push only their own branches and report the tip, current base, and intended parent. The root is the only topology writer. It keeps the chain in one `gh stack` checkout. To append a PR, run `gh stack link <stack-number> <owner-branch>`, which pushes the branch, reuses its open PR, and chains its base onto the stack's top. Then `gh stack sync` pulls it into the local stack, and `gh stack rebase` puts it on its parent's exact tip when it isn't already. Only the root PR targets trunk. Raw `git rebase` or force-push on a stacked branch breaks GitHub's stack tracking, so fall back to raw git only where `gh stack` has no equivalent.
7. **Absorb drift at the root, then re-verify what moved.** The root runs `gh stack sync` (or `gh stack rebase` when a conflict needs hands) to bring the chain onto current trunk from bottom to top. When a rebase surfaces conflicts in an owner's files, that owner fixes its own slice and the root pushes the result. A rebase rewrites every SHA above it and voids verdicts at the old SHAs. Apply the patch-id rule in `playbooks/shipping.md` at each verdict SHA. Anything that is no longer valid goes back through this playbook's step 4 before delivery. Re-run mergeability and CI after every rewritten push even when the patch-id is unchanged. The countersign rule is unchanged from Autopilot-full. A genuinely new pin raises a stop for the root's fresh countersign. Absorbing drift of landed values is not a raise.
8. **Deliver the chain.** The deliverable is one linear chain of verified PRs, reviewable bottom-up on GitHub, every link carrying its verifier verdict in the PR body or a comment. The operator reviews and lands it, with their own clicks, `gh stack merge`, or by arming merge-when-ready.

**Choosing between the autopilots.** Autopilot-full when the PRs are independent and landing authority is granted. Autopilot-stack when the operator wants review before landing, the work is sequenced or coupled, or merge authority is withheld.

**Reply:** links to the stack root and tip, a one-line verdict summary per link, and anything parked or excluded with the reason.

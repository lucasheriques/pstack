### Autopilot-stack

**You own the stack, never the landing. Hand the operator one linear `gh stack` of verified PRs to review and land.** **Autopilot-full** holds except for how verified work leaves. Each tick re-reads both playbooks from trunk, and this one wins where they differ.

1. **Run Autopilot-full's owners, minus the landing.** Owners report STACK-READY in place of merge-ready. Once you link an owner's branch into the stack, the owner only adds commits and never force-pushes it, because a force-push on a stacked branch breaks GitHub's stack tracking. They never rebase onto another branch, trunk included, never run `gh stack`, and never retarget, merge, close a PR, or arm auto-merge, because the root owns the chain's topology and the operator owns the landing. When an item depends on another, its owner branches from that item's branch, not from trunk.
2. **Give the topology one writer.** Owners push only their own branches and report each tip and its intended parent. Only you change the chain, because two writers on one chain undo each other. Keep it in one `gh stack` checkout. Append each clean PR in dependency order with `gh stack link <stack-number> <owner-branch>`, which pushes the branch, reuses its open PR, and chains its base onto the stack's top, then `gh stack sync`. Raw `git rebase` or force-push on a stacked branch breaks GitHub's stack tracking, so fall back to raw git only where `gh stack` has no equivalent. Never require `gt`. An owner takes your push as its new base and lease, and on a conflict resolves its own slice for you to push.
3. **Absorb drift at the root.** Until landing starts, apply Autopilot-full step 5's test to each link and bring the chain onto trunk bottom-up with `gh stack sync`, or `gh stack rebase` when a conflict needs hands, where the test calls for a rebase. Then apply the patch-id rule link by link, since a link's base is its parent.
4. **Deliver the chain, then keep your hands off it.** Each link carries its verdict in its PR. Once landing starts, nobody writes to the chain, because a second writer breaks a landing in flight. GitHub restacks the rest server-side as each bottom PR merges, per `playbooks/shipping.md`. A mid-landing problem goes through you to the operator, and any fix waits for the operator's go.

**Choosing between the autopilots.** Autopilot-full when the PRs are independent and landing authority is granted. Autopilot-stack when the operator wants review before landing, the work is sequenced or coupled, or merge authority is withheld.

**Reply:** catch the operator up per the **ketchup** skill, with links to the stack root and tip, a one-line verdict per link, and anything parked or excluded with the reason.
